# 04 — Trust & Reputation: native Android porting spec

Status: complete spec for the Kotlin + Jetpack Compose (Material 3 Expressive) rewrite.
Source of truth: the Flutter code at the commit this file was written against (branch `t3/explain-flutter-choice`, HEAD `623bdc9`).
Test vectors: `android-native/spec/fixtures/04-trust-reputation-vectors.json`. They were generated by an independent Python reference (hashlib plus the BIP-340 reference implementation). The native unit tests must load that file.

> Conventions in this document
> - "MUST (compat)" means a change breaks wire or data compatibility with Flutter users.
> - "PARITY" means current Flutter behaviour that the port reproduces even when it looks odd.
> - "FIX (recommended)" means a Flutter bug that can be fixed without breaking compatibility. Each one says what the fix changes.
> - String keys are the ARB keys from `lib/l10n/app_de.arb`. They map 1:1 to `R.string.<key>` in `:core:l10n` (see `android-native/tools/arb2xml.py`). Positional args follow the ARB placeholder order, not the Dart call order (see §14, R-17).

## 1. Overview and user-visible features

The domain turns physically collected meetup badges into a locally computed **Trust Score**. It also publishes privacy-preserving **aggregate reputation** to Nostr relays (kind 30078) and lets the user present it as a **Schnorr-signed QR code** (21v3). Other users can **verify** that QR or a verify string / npub, using four evidence layers (meetup badges, Lightning/zaps, Nostr social graph, NIP-05 and platform proofs). The domain also offers a **presence check** ("Person prüfen") that finds a chain of shared meetups between you and another npub. The Trust Score also drives **organizer auto-promotion**: `meetsPromotionThreshold` is consumed by `AdminStatusVerifier`.

Feature list. Every item is user-visible, small ones included:

Trust score (local)
1. Trust Score computed locally from signed, non-organizer, de-duplicated badges. Shown with 1 decimal everywhere (`toStringAsFixed(1)`).
2. Trust level with 5 internal values `NEU`, `STARTER`, `AKTIV`, `ETABLIERT`, `VETERAN`. Localized display via `levelNew`/`levelStarter`/`levelActive`/`levelEstablished`/`levelVeteran`. Each level has an icon and colour (table in §2.0).
3. Bootstrap phases (Keimphase/Wachstum/Stabil) with different promotion thresholds. Not shown in UI; consumed by organizer promotion.
4. Promotion progress bar (average of 5 criteria) and a "promoted" check icon on the home tile (home domain renders it).
5. Organizer-marker badges are excluded from the score. The QR screen shows an explanatory note ("N Meetup(s) von dir organisiert — zählt nicht zum Score…").
6. "Badges unreadable" state (encrypted badge store could not be opened). The QR screen shows a warning text instead of the empty-state hint and disables the share-card action. The home tiles show "—".

Reputation QR ("REPUTATION" screen)
7. Signed reputation QR (21v3, Schnorr over kind 21001), rendered inside a styled card (level colour, nickname, score, badges/meetups/signers, QR, signed/unsigned label).
8. Warning banner when no identity (npub/telegram/twitter) is set.
9. Stats row: badges, meetups, signers, bound.
10. Proof-status block in 5 states (all bound / partly bound / all verified / some verified / no proofs), plus a "N Plattform-Verknüpfungen aktiv" line.
11. "QR ALS BILD TEILEN": share the card plus QR as a PNG (3x pixel ratio) through the system share sheet, with subject and text.
12. "AUF RELAYS AKTUALISIEREN": force-publish the kind 30078 event. Shows a progress spinner in the button, a green/red snackbar for 3 s, and the last result text under the button.
13. AppBar action "share" opens the Reputation Card screen (disabled while badges are unreadable).
14. AppBar action "scan" opens the reputation QR scanner.
15. Empty state "NOCH KEINE BADGES" with a hint and a "QR-CODE SCANNEN" button that opens the scanner.

Reputation card ("Reputations-Profil")
16. Branded card: name, score hero, localized level pill, 5 stat tiles (badges, meetups, cities, signers, days). Empty variant when there is no data.
17. "Als Bild teilen": PNG export through the share sheet, with a busy state ("Bild wird erstellt...") and an error snackbar.
18. On open it silently creates missing claim bindings (`BadgeClaimService.ensureBadgesClaimed`). This signs kind 21002 events and saves badges.

Reputation QR scanner ("REPUTATION PRÜFEN") and result ("ERGEBNIS")
19. Live camera scanning of `21v3:`, `21v2:` and `21:` codes. Other codes are ignored silently.
20. "QR AUS GALERIE LADEN" (AppBar icon plus bottom button): decode a QR from a picked image. Snackbars for "no code", "not Einundzwanzig" and processing errors.
21. App-review demo payload `21review:einundzwanzig-meetup-demo` shows a demo dialog.
22. Result screen: status header (valid/invalid, identity or not, version chip), trust block (level, score, mini stats), proof card, live NIP-05/Lightning/social layers, platform proofs from the QR, hashed meetup list, identity card ("Signiert: …"), and a "ZURÜCK" button.

Verify string / npub ("REPUTATION PRÜFEN", orphan screen)
23. Text input (3 lines, monospace) with a paste button that pastes and verifies at once. Verify button with spinner.
24. Result header with 4 levels (full / partial / signature only / invalid), nickname, message, info rows (platform, username, "Im Event bestätigt", npub shortened).
25. Four-layer `ReputationLayersWidget`: traffic-light card ("x / 4 Beweise"), four expandable layer cards with detail rows, and an advice box.

Person check ("Person prüfen")
26. npub input (lower-cased, `nostr:` stripped) with validation error "Ungültiger npub".
27. "QR scannen": camera scanner that accepts raw npub QRs (optionally `nostr:`-prefixed) or JSON with `id.np`. Medium haptic on success.
28. Result card: self / met directly (count of shared meetups) / connected over N hops / no connection (with "not in network" variant).
29. Path visualization: You → … → This person. Each non-first node opens the npub in a Nostr app (`nostr:` URI) with an njump.me web fallback. A "gemeinsames Meetup" connector sits between nodes.
30. Trust hint box ("Je näher die Verbindung…").

Trust network hub (orphan)
31. Intro text plus one tool card, "Netzwerk-Analyse", which opens "Person prüfen".

Background behaviour (no UI)
32. Auto-publish of the reputation event after app start (home), after a badge scan, after wallet merge/cleanup, and after creating/revoking a platform proof (forced). The humanity-proof update call is a no-op (§14 R-6). Throttle: 5 minutes plus a change hash.

### 2.1 ReputationQRScreen ("REPUTATION")

Entry points (no arguments):
- App shell scan sheet → "Reputation" option (`onReputation`), pushed with a slide-up transition (offset (0,1)→0, easeOutCubic).
- Badge wallet overflow sheet → `walletShowQr` ("QR-Code anzeigen", subtitle `walletShowQrSub` "Zum Scannen vor Ort").
- Home → reputation hero tile (`_buildReputationTile`, home domain).

State: `qrData: String = ""`, `isLoading = true`, `isPublishing = false`, `user`, `trustScore: TrustScore?`, `verifiedBadgeCount`, `boundBadgeCount`, `platformProofCount`, `lastPublishInfo: String?`.

Load (runs once, on screen creation; there is no refresh when you come back to the screen):
1. `user = UserProfile.load()`.
2. `proofs = PlatformProofService.getSavedProofs()` (prefs key `platform_proofs`).
3. If the global `myBadges` is empty, set `platformProofCount` and `isLoading=false` and stop (empty view).
4. Otherwise build the QR payload (§3.9, §7.5), sign it (§7.6), and set all state. On a signer failure, Flutter has no try/catch and the spinner stays forever. FIX (recommended): catch the error and fall back to the unsigned `21:` string, plus show a snackbar.

Note: the screen reads the in-memory global `myBadges`, not `MeetupBadge.loadBadges()`. The native port reads the `BadgeRepository` in-memory state flow (badge domain).

Layout (dark background `cDark`, scroll, padding 20):

#### 2.1.1 Share QR image
1. Wait one frame so the capture boundary is laid out.
2. Capture the card composable at **3x** density as PNG. If the capture fails or returns null, return silently.
3. Share: file name `einundzwanzig_reputation.png`, MIME `image/png`, subject `Einundzwanzig Reputation` (literal), text `reputationVerified` ("Meine verifizierte Meetup-Reputation"). On Android: write to `cacheDir/share/`, FileProvider URI, `ACTION_SEND` with `EXTRA_STREAM`, `EXTRA_SUBJECT`, `EXTRA_TEXT`, `ClipData` and `FLAG_GRANT_READ_URI_PERMISSION`, then `Intent.createChooser`.
4. On exception: snackbar `repShareError(e.toString())`, red background.

#### 2.1.2 Publish to relays
`isPublishing=true; lastPublishInfo=null` → `proofs = PlatformProofService.getProofsForPublishing()` → `ReputationPublisher.publish(badges = myBadges, platformProofs = proofs, force = true)` → `isPublishing=false; lastPublishInfo = result.message` → snackbar with `result.message`, green if `success` else red, 3 s. Flutter messages are hard-coded German. The native port must localize them; see the proposed new keys in §2.10.

Tours/guides: none. (`GuideTour.reputation` exists in the enum but no tour is ever started. Its only persistence is `guide_completed_reputation=true`, written by "decline all tours".)

### 2.3 SecureQRScanner ("REPUTATION PRÜFEN") → VerificationResult ("ERGEBNIS")

Entry points: the ReputationQRScreen AppBar scan action, and its empty-state button. No arguments.

Scanner layout: background `cDark`, TopAppBar `qrScanTitle`. Action `Icons.photo_library_outlined` (cCyan), tooltip `qrLoadFromGallery`, disabled after a successful scan. Body: full-screen camera preview, a scanner overlay frame with an animated search line (`ScannerOverlay` widget, ui domain), and a bottom block (bottom 60, sides 24):
- 48dp full-width button, white 15% background, white text, radius 12, elevation 0, `Icons.photo_library` 20, label `qrLoadFromGallery`.
- 12dp, then a hint card (gradient cCard 94% → cSurface 94%, radius 14, orange 24% border, elevation-3 shadow) with `qrScanHint` (white 14, centered; contains a `\n`).

Detection (`onDetect`): ignore everything once `isScanned`. For each barcode `rawValue`:
1. If it equals the trimmed string `21review:einundzwanzig-meetup-demo`, set `isScanned`, show the demo dialog (title "Demo scan OK", English literal body, "OK" button), then reset `isScanned`. Break.
2. If it starts with `"21:"`, `"21v2:"` or `"21v3:"`, set `isScanned` and call `verifyAndShow(code)`. Break.
3. Otherwise ignore it silently (no feedback).

Gallery: pick an image (native: Photo Picker `PickVisualMedia(ImageOnly)`, no permission), then decode with ML Kit `InputImage.fromFilePath`:
- no barcodes → snackbar `qrNoCodeInImage` (orange)
- demo payload → demo dialog
- first barcode that starts with one of the 3 prefixes → `verifyAndShow`
- none match → snackbar `qrNotEinundzwanzig` (orange)
- exception → snackbar `qrProcessError(e)` (red)

`verifyAndShow(fullCode)` uses the exact parsing in §7.7. Every outcome **replaces** the scanner route with the result screen (`pushReplacement`), so "back" from the result returns to the screen before the scanner.

Result screen (`ERGEBNIS`), parameters: `isValid, version, title, subtitle, identity: Map?, hasIdentity, signerNpub?, trustLevel='', trustScore=0, badgeCount=0, verifiedBadgeCount=0, boundBadgeCount=0, meetupCount=0, signerCount=0, accountAgeDays=0, meetupList=[], badgeProof='', proofTotalCount=0, proofVerifiedCount=0, platformProofsFromQR={}`.

On open: if `isValid` and `identity['np']` is a non-empty string, load the layers in parallel for **that** npub (decoded to hex; on decode failure stop loading). The loaders are:
- `SocialGraphService.analyze(hex)` with status `qrAnalyzingNetwork`
- `ZapVerificationService.analyzeZapActivity(hex, useCache=false)` with status `qrCheckingLightning`
- NIP-05: `fetchNip05FromProfile(hex, activeRelays)`, then `Nip05Service.verify(nip05, hex)` if non-empty, with status `qrCheckingNip05`

Errors are swallowed per layer. The status text is whatever loader set it last (PARITY; native may show a combined status). SECURITY FIX (recommended): see §9 S-8 (claimed npub vs signer).

Layout (padding 20, scroll), in order:
1. Status header: colour = red if invalid, green if `hasIdentity`, else orange. 8% fill, 40% 2dp border, radius 14, padding 16. Icon `Icons.verified` / `Icons.gpp_bad` (36). Title (colour, 16, w900, letterSpacing 1). Subtitle (white60, 11). If `version > 0`, a chip "v{version}" (white10 background, white30 10 mono).
2. If valid && version ≥ 3 && trustLevel non-empty, a trust block (cCard, radius 14, level-colour 25% border, padding 14):
   - Row: 40dp circle (level colour 12%) with level icon 20; level text raw (level colour 16 w800); line `"{badgeCount} Badges · {meetupCount} Meetups · {signerCount} Signer"` (hard-coded; NEW KEY `qrStatsLine`), grey600 10; score `toStringAsFixed(1)` (level colour 24 w900 mono).
   - Mini stats (space-around): `Icons.military_tech` badgeCount `qrStatBadges` orange; `Icons.location_on` meetupCount `qrStatMeetups` cCyan; `Icons.people_outline` signerCount `qrStatSigners` cPurple; `Icons.link` boundBadgeCount `qrStatBound` green; `Icons.calendar_today` accountAgeDays `qrStatDays` grey.
3. If valid && v ≥ 3 && badgeProof non-empty, a proof card: `allVerified = proofVerifiedCount == proofTotalCount && proofTotalCount > 0`. Green + `Icons.verified`, else orange + `Icons.shield_outlined`. Text `"{proofVerifiedCount} von {proofTotalCount} Badges kryptographisch verifiziert"` (hard-coded; NEW KEY `qrProofLine`) and `"Proof: " + (proof.length > 16 ? proof[0..16] + "..." : proof)` (white24 10 mono).
4. If valid && v ≥ 3:
   - While layers load: a row with a 14dp cCyan spinner and the status text.
   - NIP-05 row (only once a result exists): valid → cCyan, `Icons.alternate_email`, title = nip05, subtitle = `domainLabel`. Invalid → red, title `qrNip05Invalid`, subtitle = nip05.
   - Lightning section (only once zapStats exists): header `Icons.bolt` + `qrSectionLightning` (amber if `totalCount > 0`, else grey). If `hasLightningProof`: row `Icons.verified_user` `qrHumanVerified` / `qrLightningActive` green. If `totalCount > 0`:

   - Platform proofs from the QR `pp` (only if non-empty): header `Icons.link` purple `qrSectionPlatforms`. Per entry: `username = data['u'] ?? data['username'] ?? bool get hasCryptoProof => sig.isNotEmpty && sigVersion > 0;
```dart
bool get isNostrSigned {                    // all four conditions
  if (sigVersion != 2) return false;
  if (!RegExp(r'^[0-9a-fA-F]{128}$').hasMatch(sig)) return false;
  if (!RegExp(r'^[0-9a-fA-F]{64}$').hasMatch(adminPubkey)) return false;
  if (BigInt.parse(sig, radix: 16) == BigInt.zero) return false;   // all-zero sig rejected
  return true;
}
bool get isClaimed => claimSig.isNotEmpty && claimPubkey.isNotEmpty;
bool get isFullyBound => hasCryptoProof && isClaimed;
```

| humanityReceiptId | String? | `content.humanity_proof.receipt_event_id` | null (the app never writes it) |

Type strictness (PARITY, important for interop): Dart casts `as int?`, `as String?`, `as bool?`, `as Map<String,dynamic>?`. A value of the wrong JSON type (e.g. `3.0` for an int field, or a string for an int) throws, and Flutter then **drops the whole event** for that relay (`tally.failed`). A lenient native parser is fine for reading. The native **writer** must emit exactly the types in §3.10 so Flutter readers accept it.

## 5. Network

### 5.1 Relays
`RelayConfig.getActiveRelays()`: defaults `wss://relay.damus.io`, `wss://nos.lol`, `wss://relay.nostr.band`, `wss://nostr.einundzwanzig.space` minus disabled ones, plus custom relays. De-duplicated, order preserved (defaults first). Timeouts: `relayTimeout = 8 s`, `publishTimeout = 5 s`. Max inbound frame 512 KiB (larger frames are dropped before parsing).

### 5.2 Publish kind 30078 (`ReputationPublisher.publish`)
Order of operations (exact):
1. If `!SigningService.canSign()` → `PublishResult(false, 0, msg "Kein Schlüssel vorhanden")`.
2. If `badges.isEmpty()` → `(false, 0, "Keine Badges vorhanden")`.
3. If `!force && !shouldPublish(badges)` → `(true, 0, "Reputation ist aktuell — kein Update nötig")`. shouldPublish = `now - last >= 300_000 ms` AND `contentHash(badges) != lastHash`.
4. `user = UserProfile.load()`.
5. Best-effort, sequential: `SocialGraphService.getMyStats()` with a 10 s timeout (on timeout → `SocialStats.empty()`; on error → null and a warn log), then `ZapVerificationService.getMyStats()` with the same handling, then `HumanityProofService.getProofForPublishing()` (error → null).
6. Build content (§3.10), sign kind 30078 with tags `[["d","einundzwanzig-reputation"],["v","2"],["client","einundzwanzig-meetup-app"]]`, content = compact JSON of the content map.
7. Send to relays **sequentially**. For each relay: connect (timeout 5 s); send `["EVENT", {id, pubkey, created_at, kind, tags, content, sig}]` (exactly these keys, this order); wait a fixed **2 s**; close; count a success. Errors are logged and the loop goes on. There is no `OK` parsing (PARITY; FIX optional: read `["OK", id, true|false, msg]` within the 2 s window and only count accepted ones).
8. `savePublishStatus(badges)` runs **always** at this point, even when relayCount = 0 (PARITY; FIX recommended: save only if relayCount > 0).
9. Return `(relayCount > 0, relayCount, signed.id, relayCount > 0 ? "Reputation auf N Relays aktualisiert" : "Konnte an keinen Relay senden")`.
10. Any exception → `(false, 0, "Publish-Fehler: $e")`.

`publishInBackground(badges)` is fire-and-forget `publish(badges)`. It runs non-forced and without platform proofs (see R-5). Native: launch in an application-scoped `CoroutineScope(SupervisorJob() + Dispatchers.IO)`. If you use WorkManager (optional, `NetworkType.CONNECTED`), note that external signers (NIP-55 Amber / NIP-46) may need UI and the work must then be skipped.

Social/zap stats themselves (`getMyStats`): network-heavy, owned by the social/zap domains. Social does up to 20 contact-list fetches plus up to 10 admin follow lists, each relay sequential with an 8 s timeout. This is why the 10 s timeout exists.

### 5.3 Fetch kind 30078 (`fetchByNpub` / `fetchByPubkeyHex`)
- `fetchByNpub`: empty → null; bech32 decode fails → null; else `fetchByPubkeyHex`.
- Relays are tried **sequentially** in `getActiveRelays()` order. The first non-null result wins (not the newest across relays; PARITY, see R-9). Exceptions → next relay.
- Per relay: connect (timeout 8 s), subscription id `"rep-fetch-" + 16 lowercase hex chars` from 8 bytes of `SecureRandom` (MUST be cryptographically random; security M4). Send:
  `["REQ","rep-fetch-<hex>",{"kinds":[30078],"authors":["<hex>"],"#d":["einundzwanzig-reputation"],"limit":1}]`
- Message handling:
  - `EVENT` with ≥3 elements: build the event from `msg[2]` (missing fields default `''`/0/[]). Require `isValid()` (§7.2), else count it as failed and continue. Require `event.pubkey == pubkeyHex` (exact string compare), else ignore. Then `jsonDecode(content)` must be an object, else failed. Then parse `ReputationEvent` and complete with it (the first one wins).
  - `EOSE` → complete null.
  - socket error / done → complete null.
  - Overall wait timeout 8 s → null. Afterwards send `["CLOSE","rep-fetch-<hex>"]` and close the socket.
- Flutter does NOT check `kind == 30078` nor the `d` tag on received events. FIX (recommended, compatible): apply the same `answersFilter` check as other services (kinds, authors, `#d`). Among multiple events, prefer the highest `created_at` that is ≤ now + 600 s.

### 5.4 Other network used by screens in this domain (owned elsewhere; summarized)
- NIP-05: `GET https://<domain>/.well-known/nostr.json?name=<name>` (name/domain lower-cased), timeout 5 s, body ≤ 64 KiB, UTF-8 decode, `names[name] == expectedHex`. Profile nip05 from kind 0 on the first 2 relays.
- Zaps: kind 9735 receipts, `#p` (received) or `#P` (sent), `since = now − 180 d`, limit 100, first 3 relays, plus provider validation.
- Social: kind 3 contact lists. AdminRegistry from relays.
- Co-attendance graph (`verifyPerson`): kind 30079 data, owned by the co-attendance domain.

No HTTP portal API calls in this domain. No retries anywhere (the relay loop acts as failover). No rate limits other than the 5-minute publish throttle.

## 7. Crypto and encoding

All hashes are SHA-256 over UTF-8 bytes. The output is **lowercase hex**. Concatenations are plain string concatenation, with no separators other than those shown.

### 7.1 Badge proof hashes (from `badge.dart`, verbatim)
```dart
String get proofId {                       // per badge, for v1
  if (sigId.isNotEmpty) return sigId;
  if (sig.isNotEmpty) return sig.substring(0, 64);           // throws if sig.length < 64 (PARITY: guard natively, see R-12)
  final data = '$id-$meetupName-${date.toIso8601String()}-$blockHeight';
  return sha256.convert(utf8.encode(data)).toString().substring(0, 64);
}
String get claimProofId {
  if (!isClaimed) return '';
  final data = '$sig|$claimSig|$claimPubkey';
  return sha256.convert(utf8.encode(data)).toString();
}
static String generateBadgeProofV2(List<MeetupBadge> badges) {
  final bound = badges.where((b) => b.isFullyBound).toList();
  if (bound.isEmpty) return '';
  bound.sort((a, b) => a.claimTimestamp.compareTo(b.claimTimestamp));   // see R-10 (stability)
  final proofChain = bound.map((b) => b.claimProofId).join('|');
  return sha256.convert(utf8.encode(proofChain)).toString();
}
static String generateBadgeProof(List<MeetupBadge> badges) {          // v1
  if (badges.isEmpty) return '';
  final sorted = List<MeetupBadge>.from(badges)..sort((a, b) => a.date.compareTo(b.date));
  final proofChain = sorted.map((b) => b.proofId).join('|');
  return sha256.convert(utf8.encode(proofChain)).toString();
}
```
Nobody re-computes these hashes on the verifier side (verifiers only display them), so exact reproduction matters for consistency, not for interop. Still implement them exactly as above. Use a stable sort (Kotlin `sortedBy`). Dart's sort is insertion sort (stable) for ≤ 33 elements and unstable dual-pivot quicksort above that.

`DateTime.toIso8601String()` (Dart) format: `YYYY-MM-DDTHH:mm:ss.mmm` plus `uuu` microseconds only if non-zero, plus `Z` only for UTC DateTimes. Local DateTimes carry no offset. Years outside 0..9999 use a signed 6-digit form. The native badge model must keep both the instant and the `isUtc` flag (or the original string) to reproduce this. See R-11.

### 7.2 Nostr event id and signature
NIP-01 serialization (see §6). JSON string escaping must follow NIP-01 / Dart `jsonEncode`:
- `"` → `\"`, `\` → `\\`
- control chars: `\b \t \n \f \r`, others `\u00xx`
- `/` is NOT escaped, non-ASCII is emitted raw (UTF-8)
- no whitespace between tokens; numbers as integers

Do NOT use Android `org.json` (it escapes `/`) and do NOT use Gson defaults (they HTML-escape `<>&=` and `'`). Use the shared NIP-01 serializer from the Nostr core domain. Schnorr: BIP-340 over secp256k1 (`fr.acinq.secp256k1:secp256k1-kmp`), 64-byte sig → 128 lowercase hex, 32-byte x-only pubkey → 64 hex. Random 32-byte aux per signature.

### 7.3 Meetup list hash (privacy of meetup names)
```dart
reputation['ml'] = uniqueMeetups.take(10).map((name) {
  final hash = sha256.convert(utf8.encode('21meetup:$name')).toString();
  return hash.substring(0, 12);          // 12 hex = 48 bit
}).toList();
```
`uniqueMeetups` is a LinkedHashSet of `meetupName` over the counted badges (signed && !organizer), in the order of `myBadges`. Names are exact (case-sensitive, not trimmed). Vector: `sha256("21meetup:Aschaffenburg")[:12] = d4ca521ba896`.

### 7.4 Publish change hash
```dart

    '|${badges.map((b) => b.meetupName).toSet().length}'
    '|${badges.map((b) => b.adminPubkey).where((p) => p.isNotEmpty).toSet().length}';
```

Vector: `"3|2|2|1"` → `08e47cd91958e564`.

### 7.5 QR payload JSON
Compact JSON (`jsonEncode`): no spaces, key order as in §3.9. Number typing is MUST (compat):
- `v`, `bc`, `vc`, `mc`, `si`, `ad`, `bb`, `pv`, `tc`, `t` are JSON **integers** (no `.0`).
- `sc` is a JSON number. Dart writes doubles with a decimal point (`7.0`, `0.0`, `12.3`), and readers accept any number.

With kotlinx.serialization use `JsonPrimitive(Int/Long)` for ints and `JsonPrimitive(Double)` for `sc`.

### 7.6 QR signing and the string format
```dart
final jsonString = jsonEncode(qrPayload);
final signResult = await BadgeSecurity.signQRv3(jsonString);  // kind 21001, tags [], content = jsonString
final base64Json = base64Encode(utf8.encode(jsonString));       // STANDARD alphabet, WITH '=' padding
secureQrData = signResult.isNostr
  ? "21v3:$base64Json.${sig}.${eventId}.${createdAt}.${pubkeyHex}"
  : "21:$base64Json.${signResult.signature}";                   // signature is '' → ends with "."
```
- `signQRv3`: if `!canSign()`, return `isNostr=false` with empty fields. Else `SigningService.signEvent(kind: 21001, tags: [], content: jsonString)`.
- Layout: `21v3:` + base64 + `.` + 128-hex sig + `.` + 64-hex id + `.` + decimal created_at (seconds) + `.` + 64-hex pubkey.
- The QR is encoded in byte mode with error correction **L**, version auto. Typical length is about 900–1000 chars (the vector is 987). That is close to the L-level byte capacity of version ~23. ZXing `QRCodeWriter` with `EncodeHintType.ERROR_CORRECTION=L`, `MARGIN=0` (padding is drawn by the card), `CHARACTER_SET=ISO-8859-1` (all chars are ASCII).

### 7.7 QR parsing/verification (scanner, verbatim logic)
```dart
final isV3 = fullCode.startsWith("21v3:"); final isV2 = fullCode.startsWith("21v2:");
String clean = (isV3 || isV2) ? fullCode.substring(5) : fullCode.substring(3);
final parts = clean.split('.');
if (isV3 && parts.length >= 5) {
  final json = utf8.decode(base64.decode(parts[0]));
  final r = BadgeSecurity.verifyQRv3(jsonData: json, signature: parts[1], eventId: parts[2],
               createdAt: int.tryParse(parts[3]) ?? 0, pubkeyHex: parts[4]);
  r.isValid ? showV3(jsonDecode(json), signerNpub: r.signerNpub, msg: r.message)
            : showFailed(title: qrSigInvalid, subtitle: r.message);
  return;
}
if (isV2 && parts.length >= 3) { /* verifyQRLegacy → ALWAYS invalid */ showFailed(qrSigInvalid, legacyMsg); return; }
if (!isV3 && !isV2 && parts.length >= 2) { /* verifyQRLegacy → ALWAYS invalid */ showFailed(qrSigInvalid, legacyMsg); return; }
showFailed(title: qrFormatUnknown, subtitle: qrCantRead);
// any exception (bad base64, bad UTF-8, bad JSON, cast errors) → showFailed(qrReadError, qrProcessError(e))
```
`verifyQRv3` steps, in order (messages are the hard-coded German strings from §2.10):
1. Any of pubkey/sig/id empty → invalid "Fehlende Signatur-Daten".
2. pubkey not 64 hex (case-insensitive) → "Ungültiges Pubkey-Format".
3. sig not 128 hex → "Ungültiges Signatur-Format".
4. Construct `Event(id, pubkey, createdAt, 21001, [], json, sig)` with **verify=true**. An invalid event THROWS `'Invalid event'` → caught → message `"Fehler: Invalid event"` (so the "Schnorr-Signatur UNGÜLTIG!" branch is effectively unreachable).
5. Valid → `isValid=true, version=3, signerNpub=bech32(pubkey), message "Schnorr-Signatur verifiziert ✓"`.

Base64 decode: Dart `base64.decode` accepts standard and URL-safe alphabets and requires correct padding. Use `java.util.Base64.getMimeDecoder()`, or normalise `-_` → `+/` and use `getDecoder()`.

v3 result mapping (`showV3`):
- `id = data['id'] ?? {}`, `rp = data['rp'] ?? {}`, `pf = data['pf'] ?? {}`, `pp = data['pp'] ?? {}`
- `hasIdentity = id.np || id.tg || id.tw` is a non-empty `toString()`
- title `qrVerified`, subtitle = verify message
- `trustLevel = rp.lv ?? ''`, `trustScore = (rp.sc as num?)?.toDouble() ?? 0`, `badgeCount = rp.bc ?? 0`
- `verifiedBadgeCount = rp.vc ?? pf.vc ?? 0`, `boundBadgeCount = rp.bb ?? pf.bb ?? 0`
- `meetupCount = rp.mc ?? 0`, `signerCount = rp.si ?? 0`, `accountAgeDays = rp.ad ?? 0`, `meetupList = rp.ml ?? []`
- `badgeProof = pf.bp ?? ''`, `proofTotalCount = pf.tc ?? 0`, `proofVerifiedCount = pf.vc ?? 0`, `platformProofsFromQR = pp`

The payload `v` is not checked. Legacy result mappings (unreachable today, because legacy verification always fails; keep them for completeness):
- v2: `qrVerifiedV2`/`qrV2Subtitle`, badgeCount = `data.c`, meetupCount = `data.m`
- v1: `qrVerifiedV1`/`qrV1Subtitle`, identity `{n: data.u ?? 'Anon'}`

### 7.8 Platform proof verify string
Format `21rep::<npub>::<platform>::<username>::sig=<128 hex>` (split on `::`, ≥ 5 parts; `npub` must start with `npub1`; sig must be 128 chars). The signature is NOT verified (format + hex check only; §9 S-9).

### 7.9 Number formatting (MUST for byte parity of the payload, SHOULD for UI)
- Dart `x.toStringAsFixed(1)` rounds the **exact binary value** half-up: `2.75→"2.8"`, `0.35→"0.3"`, `1.45→"1.4"`, `0.05→"0.1"`. Kotlin: the shared `Double.toStringAsFixed(fractionDigits)` from `:core:common` (`space.einundzwanzig.meetup.core.common.dart`, DartCompat.kt), which also keeps the `-` for `-0.0`. Do NOT use `String.format("%.1f")`: it uses the default locale (German gives `7,3`) and rounds the shortest decimal representation. Payload values: `double.parse(score.toStringAsFixed(1))` → `score.toStringAsFixed(1).toDouble()`.
- Dart `double.round()` (used for `progress.score`) rounds half away from zero: `Math.round` matches for x ≥ 0. For negatives use `sign(x)*floor(abs(x)+0.5)`.
- Always `Locale.ROOT` for number/date formatting that goes into a payload, a hash or a URL. `Locale.ROOT` does **not** make case mapping Dart-compatible: Java `lowercase(Locale.ROOT)` applies final sigma (`"ΟΔΟΣ"` → `"οδος"`, Dart `"οδοσ"`) and maps `"İ"` (U+0130) to `"i\u0307"` (Dart `"i"`), and `uppercase()` maps `ß` → `SS` (Dart keeps `ß`). Every Dart `toLowerCase()`/`toUpperCase()`/`trim()` that feeds a key, hash or comparison (e.g. the `nd:` key in §7, `_badgeToEventId`) uses `DartString.lower/upper/trim` (spec 02 §8.14). The npub input normalisation (§2.7) uses it too: `"npub1…İ…"` lower-cases to a valid npub in Dart but not with Java.

## 8. Business rules and algorithms

### 8.1 Trust score (`TrustScoreService.calculateScore(badges, firstBadgeDate, coAttestorMap = null)`)
Verbatim core (keep the order and the constants):
```dart
final trustedForPhase = badges.where((b) => b.isNostrSigned && !b.isOrganizer).toList();
final phase = _determinePhase(trustedForPhase);        // distinct non-empty signerNpub: >=6 stabil, >=2 wachstum, else keimphase
final thresholds = TrustConfig.phases[phase]!;
if (badges.isEmpty) return _emptyScore(phase, thresholds);

final trusted = badges.where((b) => b.isNostrSigned && !b.isOrganizer).toList()
  ..sort((a, b) => a.date.compareTo(b.date));          // ascending, stable
final seen = <String>{}; final trustedBadges = <MeetupBadge>[];
for (final b in trusted) { if (seen.add(MeetupBadge.identityKey(b))) trustedBadges.add(b); }   // oldest wins
if (trustedBadges.isEmpty) return _emptyScore(phase, thresholds);

final meetupBadges = trustedBadges.where((b) => !b.isEvent).toList();
final uniqueMeetups = meetupBadges.map((b) => b.meetupName).toSet();             // events EXCLUDED
final uniqueSigners = trustedBadges.map((b) => b.signerNpub).where((s) => s.isNotEmpty).toSet(); // events INCLUDED
final uniqueCities = uniqueMeetups;
final accountAge = firstBadgeDate != null ? DateTime.now().difference(firstBadgeDate) : Duration.zero;

final weeklyCount = <int,int>{};
final sortedBadges = List.of(trustedBadges)..sort((a, b) => b.date.compareTo(a.date));   // DESC, stable
for (final badge in sortedBadges) {
  final weekNumber = badge.date.difference(DateTime(2024)).inDays ~/ 7;   // DateTime(2024) = LOCAL 2024-01-01 00:00
  weeklyCount[weekNumber] = (weeklyCount[weekNumber] ?? 0) + 1;
  if (weeklyCount[weekNumber]! > 2) { add(BadgeValue all zeros); continue; }      // 3rd+ newest... i.e. the OLDEST in the week are zeroed
  final coData = coAttestorMap?[_badgeToEventId(badge)];
  final attendeeCount = coData?.attendeeCount ?? 1;
  final veteranCount = coData?.veteranCount ?? 0;
  final coAttestorBonus = log(attendeeCount + 1) / log(2);                // =1.0 exactly when no data
  final signerBonus = 1.0 + (veteranCount * 0.3);
  final ageWeeks = DateTime.now().difference(badge.date).inDays / 7.0;     // integer days / 7.0
  final decayFactor = pow(0.5, ageWeeks / 26.0).toDouble();
  final presenceFactor = badge.presenceVerified ? 1.0 : 0.7;
  final totalValue = 1.0 * coAttestorBonus * signerBonus * decayFactor * presenceFactor;
  add(BadgeValue(badge.id, badge.meetupName, 1.0, coAttestorBonus, signerBonus, decayFactor, totalValue, attendeeCount, veteranCount));
}
final maturityScore = min(1.0, accountAge.inDays / 180.0) * 1.0;
final verifiedMeetups = trustedBadges.where((b) => b.presenceVerified).map((b) => b.meetupName).toSet(); // NOTE: events INCLUDED here (PARITY)
final unverifiedOnly = uniqueMeetups.difference(verifiedMeetups);
final effectiveDiversity = verifiedMeetups.length + 0.5 * unverifiedOnly.length;
final diversityScore = (log(effectiveDiversity + 1) / log(2)) * (log(max(uniqueSigners.length, 1) + 1) / log(2)) * 1.5;
final qualityScore = badgeValues.isNotEmpty ? (sum(signerBonus) / badgeValues.length) * 1.2 : 0.0; // capped (0) values included
final activityScore = sum(totalValue);
final totalScore = activityScore * (1 + maturityScore) * (1 + diversityScore * 0.1);
```
Time semantics (MUST for parity):
- `difference()` is an absolute duration in microseconds. `inDays` truncates toward zero. `~/` truncates toward zero, so days −6..+6 around the anchor all map to week 0.
- Kotlin: `Duration.between(a, b).toDays()` (truncates toward zero), then `/ 7` on Long. Anchor = `LocalDate.of(2024,1,1).atStartOfDay(ZoneId.systemDefault()).toInstant()`.
- Future-dated badges give a negative `ageWeeks`, so `decay > 1` (PARITY).
- Inject the clock (`TimeSource`) for tests.
- Use `ln(x)/ln(2.0)` for the log2 terms, not `log2()`, to keep the IEEE results identical.

Progress map and promotion (insertion order matters):
```
badges : current = trustedBadges.length,   required = minBadges,           label 'Badges (Nostr-verifiziert)'
meetups: current = uniqueMeetups.length,   required = minUniqueMeetups,    label 'Verschiedene Meetups'
signers: current = uniqueSigners.length,   required = minUniqueSigners,    label 'Verschiedene Ersteller'
age    : current = accountAge.inDays,      required = minAccountAgeDays,   label 'Account-Alter (Tage)'
score  : current = totalScore.round(),     required = promotionScore.round(), label 'Trust Score'
```
`meetsPromotionThreshold` = all `met`. `promotionReason` = the reason for the FIRST unmet entry:
- badges: `'Noch ${r-c} Badges sammeln ($c/$r)'`
- meetups: `'Noch ${r-c} verschiedene Meetups besuchen ($c/$r)'`
- signers: `'Badges von ${r-c} weiteren Erstellern nötig ($c/$r)'`
- age: `'Noch ${r-c} Tage warten ($c/$r Tage)'`
- score: `'Trust Score $c / $r'`

If all are met: `'Alle Bedingungen erfüllt! Du kannst jetzt Meetup-Tags erstellen.'`. Not shown in the UI today; keep it, localization is optional.

Empty score (`badges` empty OR no trusted badge left): all numbers 0, `meetsPromotionThreshold=false`, reason `'Besuche Meetups und sammle Badges!'`, `badgeValues=[]`, phase/thresholds as computed. Progress labels `'Badges','Meetups','Ersteller','Tage','Score'` with current 0 and required from the thresholds (score required = `promotionScore.round()`).

Important consequences (PARITY):
- Claim binding is NOT required for the score (REPUTATION.md claims otherwise; code wins).
- The phase is computed from the NON-deduplicated trusted list.
- `uniqueCities == uniqueMeetups`.
- `firstBadgeDate` is supplied by the caller. Every caller uses the earliest `date` over **all** badges, including organizer markers and legacy ones.

`_badgeToEventId(b)` = `b.meetupName.toLowerCase().replaceAll(' ', '-') + '-' + b.date.toIso8601String().substring(0, 10)`. Only used as a key into `coAttestorMap`.

`identityKey(b)` (shared with the wallet de-duplication; MUST be identical to the badge domain):

### 8.2 Bridge score (unused in prod; port with tests)
`if (badges.length < 3) 0`; `cities = distinct meetupName of !isEvent`; `if (cities.size <= 1) 0`; else `cities.size * max(distinctNonEmptySigners(all badges), 1)`. No trust filtering.

### 8.3 Sybil heuristics (unused in prod; port with tests)
Over the given badges (no filtering), in this order:
1. distinct non-empty signers == 1 && badges.size > 3 → `'Alle Badges von nur einem Ersteller'`.
2. Group by `date.toIso8601String().substring(0,10)`. If the max per day > 3 → `'$max Badges an einem Tag'`.
3. If `coAttestorMap != null`: lonely = badges with no entry or `attendeeCount <= 1`. If lonely == size && size > 2 → `'Kein Badge hat Co-Attestors'`.

Empty → `[]`.

### 8.4 Levels and display
Local level thresholds 3/10/20/40 (§3.4). Relay level `_scoreToLevel(basic)`: ≥8 `VETERAN`, ≥5 `ETABLIERT`, ≥2 `AKTIV`, >0 `STARTER`, else `NEU`. The two scales differ: the QR carries the local level, the relay event carries the basic level (PARITY, MUST keep for meaning; R-3).

### 8.5 Relay basic score (`_calculateBasicScore`)
```dart
double score = 0;
```

### 8.10 Verify string / npub (`PlatformProofService.verifyProofString(input, expectedUsername = null)`)
1. `parsed = parseVerifyString(input)`. If null: if `input.trim()` starts with `npub1` → `verifyByNpub`; else `invalid`, "Ungültiges Format. Erwartet: 21rep::npub::plattform::username::sig=...".
2. "Signature check" = bech32 decode ok and the sig is 128 chars parseable as hex. Else `invalid`, "WARNUNG: Signatur ungültig! Dieser Verify-String wurde manipuliert." (§9 S-9).
3. `expectedUsername` is unused by callers today; on a case-insensitive mismatch → `invalid` with the WARNUNG username message.
4. `rep = fetchByNpub(npub)`. If null → `signatureOnly`, "Signatur gültig ✓ — Aber keine Reputation auf Relays gefunden.".
5. `proofInEvent = rep.platformProofs[platform] is Map && map['username'] == parsed.username` (exact, case-sensitive).
6. `hasBindings = rep.boundBadges > 0`; `allBound = rep.boundBadges == rep.totalBadges && rep.totalBadges > 0`. Then:
   - proofInEvent && hasBindings && allBound → `full`, "Identität und Reputation vollständig bestätigt ✓"
   - proofInEvent && hasBindings → `partial`, "Reputation teilweise bestätigt — {bound} von {total} Badges gebunden."
   - hasBindings → `partial`, "Reputation verifiziert, aber Plattform-Proof nicht im Event gefunden."
   - else → `signatureOnly`, "Signatur gültig, aber keine gebundenen Badges."
7. Exception → `invalid`, "Verifikations-Fehler: $e".

`verifyByNpub(npub)`:
- rep null → `signatureOnly`, "Keine Reputation auf Relays gefunden für diesen npub."
- else level = `partial` if bound > 0, else `signatureOnly`. Messages: "Reputation gefunden — aber kein Plattform-Proof. Identitäts-Verknüpfung nicht bestätigt." / "Reputation gefunden, aber keine gebundenen Badges.". `proofInEvent=false`.

## 9. Security measures to preserve

- **S-1 (Audit C1)**: only `isNostrSigned` (v2 Schnorr format) and non-organizer badges count toward the score and the phase. Legacy v1/v0 never count. Legacy QR formats (`21:` / `21v2:`) are ALWAYS rejected (`verifyQRLegacy` returns invalid). `signLegacy` is disabled. Keep both stubs returning invalid.
- **S-2**: organizer marker badges (self-issued) are excluded, even when they carry a valid signature (test "auch Marker mit Signatur erhöhen keine Reputation").
- **S-3 (field test July 2026)**: de-duplicate by `identityKey`, oldest wins, so re-scans and rolling-QR re-signatures cannot inflate the score. Frequency cap: 2 per week.
- **S-4**: presence-unverified badges count 0.7 in value and 0.5 in diversity.
- **S-5 (Audit M4)**: subscription ids come from a CSPRNG (8 bytes → 16 hex); relay frames > 512 KiB are dropped.
- **S-6 (Audit H2/M1)**: every relay event is verified (id recomputation + BIP-340) before use, including the 10-digit `created_at` rule. The fetched event's pubkey must equal the requested author.
- **S-7 privacy**: the relay event carries only aggregates. No meetup names, places or dates (`since` is month precision only). The QR carries meetup names only as 48-bit salted-prefix hashes (`21meetup:`). Platform proofs are published only if the user created them.
- **S-8 (gap, FIX recommended)**: the scanner verifies that the QR was signed by `pubkeyHex` but never checks that it equals the claimed `id.np`. It then loads the NIP-05/social/zap layers for the CLAIMED npub. An attacker can sign with their own key while claiming a victim's npub, and the screen shows "VERIFIZIERT" plus the victim's layers. Native port: compute `signerNpub` and compare it with `id.np` (case-insensitive). On mismatch, show a prominent warning (a new string, e.g. `qrIdentityMismatch`), treat `hasIdentity` as false, and load layers for the signer. This stays compatible with existing QRs: genuine Flutter QRs always have `np == signer` when `np` is present, because both come from the same identity.
- **S-9 (gap)**: the platform proof "signature" in verify strings and in QR `pp` entries is never cryptographically checked: the 21rep sig signs a kind 21003 event whose `created_at` is not part of the string. The UI label "Signatur verifiziert" is misleading. Native: keep the format check, but label the result as "verknüpft (unbestätigt)" unless the proof is also present in the author's signed kind 30078 event (`proofInEvent`). Do not claim cryptographic verification.
- **S-10**: QRs have no expiry. `t` (ms) is informational. Optional native enhancement: show the QR age.
- **S-11**: the QR screen and card never contain private keys. Signing goes through SigningService (Amber/NIP-46 keep the key external).
- **S-12**: share images go through a FileProvider in the cache dir with read-grant flags only. No world-readable files.

The Security docs (`SecurityAudit.md`, `SecurityChangelog.md`) mention a "Co-Signatur" (`participantSig`) model. It was superseded by the claim binding (kind 21002, `claimSig`/`claimPubkey`). Do not implement `participantSig`.

## 14. Risks and compatibility pitfalls

- **R-1 Doc vs code**: REPUTATION.md says unbound badges don't count and shows a reduced event JSON. The code counts every `isNostrSigned && !isOrganizer` badge and publishes more fields (`retroactive_badges`, `social`, `lightning`, `platform_proofs`). Port the CODE.
- **R-2 JSON number typing (MUST)**: Flutter readers cast `as int?`. Emitting `3.0` for an int field makes Flutter drop the whole reputation event, or show "LESEFEHLER" for a QR. Only `stats.score` and `rp.sc` may be doubles.
- **R-3 Two level scales**: QR `lv` uses the local 3/10/20/40 scale on `totalScore` (unbounded). The relay `stats.level` uses 2/5/8 on a 0..10 basic score. Never unify them; both are "wire meaning".
- **R-4 Publisher counts ALL badges** (markers and unsigned included) while the QR counts only the trusted ones. See §8.8 for the recommended fix; it is wire-safe either way.
- **R-5 Background publishes drop platform proofs**: `publishInBackground` passes no proofs, and kind 30078 is replaceable. Any auto-publish after a count change removes `platform_proofs` from relays, downgrading verify-string results from `full` to `partial`. FIX (recommended): always load `getProofsForPublishing()` inside `publish` when `platformProofs == null`.
- **R-6 Humanity screen no-op**: `publishInBackground([])` hits the "no badges" guard. FIX: pass the current badges and `force = true`, so a newly verified humanity proof gets published.
- **R-7 Throttle state saved on total failure**: after 0 successful relays, the next auto-publish is suppressed until counts change. FIX: save only on success. The reputation keys also survive an identity switch (§4).
- **R-8 Unsigned QR**: without a signer, the QR is `21:<b64>.`, which every scanner rejects. The card label "Schnorr-signiert" is driven by `hasIdentity`, not by the signature. Fix the label; consider showing a "sign-in needed" hint instead of an unverifiable QR.
- **R-9 Fetch picks the first relay's event**, not the newest, and doesn't check kind/d-tag. Prefer the newest valid one; keep the author check.
- **R-10 Sort stability**: Dart `List.sort` is stable only for ≤ 33 elements. Ties in `claimTimestamp` are common, because retroactive claims are created in a loop within the same second. With > 33 bound badges the v2 hash can differ between Flutter and native. Harmless (no verifier recomputes it), but don't build features that compare hashes across implementations.
- **R-11 DateTime zone semantics**: badge dates are Dart DateTimes that are UTC or local depending on the stored ISO string. `identityKey`'s fallback, `_badgeToEventId`, `since`, the sybil day buckets and `proofId`'s fallback ISO string all use the stored zone's calendar fields. The week anchor `DateTime(2024)` is LOCAL. The native badge model must preserve `isUtc`, and tests must pin the default time zone.
- **R-12 `proofId` crash path**: `sig.substring(0,64)` throws for 0 < sig.length < 64 when sigId is empty. That aborts QR generation and the publish (caught → "Publish-Fehler"). Natively, guard by falling back to the hash. This changes the v1 hash only for corrupt badges.
- **R-13 Number formatting**: use the shared `Double.toStringAsFixed` (`:core:common`) and `Locale.ROOT`. A German locale with `String.format` produces `7,3`, which yields a QR whose `sc` breaks JSON or reads as a string.
- **R-14 JSON escaping for ids**: event ids must be computed with NIP-01/Dart escaping (no `\/`, raw UTF-8). The QR content string is signed verbatim, so serialize once and reuse the exact same string for base64 and signing.
- **R-15 QR density**: about 1000 chars at EC L. Keep a ≥ 220dp render size and a white quiet zone. Don't switch to EC M/H (capacity) and don't render it dark.
- **R-16 Security gaps carried over**: S-8 (claimed npub ≠ signer), S-9 (platform proof signatures not verified), S-10 (no expiry). The fixes are compatible; implement them.
- **R-17 Swapped l10n args**: Flutter passes `(bound,total)` into `repBoundOf(total,bound)` and `(verified,total)` into `repVerifiedSchnorr(total,verified)`. The generated Android strings use ARB placeholder order (`%1$s`=total, `%2$s`=bound/verified). Call them with `(total, bound)`.
- **R-18 Orphan screens**: ReputationVerifyScreen and TrustNetworkHubScreen have no entry point. Porting them without wiring keeps parity. Wiring them is a product decision.
- **R-19 Signer prompts**: the QR screen signs on every open (kind 21001), and publishes sign 30078. With Amber/NIP-46 this can prompt the user. The NIP-46 permission list already contains 21001 and 30078 (spec 01 §6.2 `requestedPerms`) and must keep them; background publishes must not block on UI.
- **R-20 Layer scoring quirks** (PARITY): account age > 30 days makes the identity layer "active" in the count even without NIP-05/platforms, while its card says "fehlt". Event badges with verified presence raise `effectiveDiversity` although they don't count as meetups. QR `mc` includes event badges while the score's `uniqueMeetups` excludes them. Proof card `vc` (all crypto badges) can exceed `tc` (trusted only).
- **R-21 VerifyPerson npub scanner** cannot read real reputation QRs (base64-wrapped). See the §2.7.1 FIX.
- **R-22 Share-card data source**: the card screen loads from storage and runs claim creation (side effects, signer prompts), while the QR screen uses the in-memory list. Make sure the repository emits the updated badges so both screens agree.
